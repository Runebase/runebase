# v30.2 upgrade — scope analysis

Branch `30.2` created from `master` (`903a1f066`) on 2026-08-25.
**No code changes yet — this document is the scope assessment only.**

Target: [Qtum v30.2](https://github.com/qtumproject/qtum/releases/tag/v30.2)
(`refs/qtum/v30.2` = `e2ead53c87`), based on Bitcoin Core 30.2 and absorbing
upstream 29.2, 30.0, 30.1, 30.2.

## Verdict

**Comparable in size to the 27.1 -> 29.1 upgrade we just completed, but
lower in consensus risk and higher in user-migration risk.**

There is **no new consensus fork** in v30.2 — the `consensus/params.h`
churn is structural (BIP9Deployment gained `period`/`threshold` fields,
`vDeployments` became a `std::array`). Unlike 29.1, which carried Pectra,
this upgrade activates nothing on its own. The danger has moved from
consensus to **wallet compatibility**: legacy BDB wallets are gone.

## Measured scope

Upstream churn (`git diff --shortstat refs/qtum/v29.1 refs/qtum/v30.2`):

| | files | insertions | deletions |
|---|---|---|---|
| **v29.1 -> v30.2 (this upgrade)** | 1554 | 70,767 | 94,679 |
| v27.1 -> v29.1 (completed) | 1947 | 124,274 | 86,022 |

Note the shape: a **net deletion of ~24k lines**, dominated by legacy
wallet removal and locale pruning.

The number that actually matters is the *replay surface*: Runebase's own
delta measured against a mechanically renamed Qtum v29.1 tree (procedure
per CLAUDE.md; both trees renamed and diffed for this analysis):

| metric | count |
|---|---|
| files where Runebase differs from renamed qtum v29.1 | **120** |
| of those, **also changed upstream** -> real merge needed | **60** |
| of those, upstream untouched -> clean replay | **59** |
| Runebase-modified but **deleted upstream** | **1** |
| Runebase-only files (not in upstream at all) | 4 |

Two findings that shrink the work considerably:

- **The EVM/contract layer has ZERO conflicts.** No file under
  `src/runebase/` or `src/eth_client/` is both Runebase-modified and
  upstream-modified. **The RIP-1 gate in `getMinGasPrice()` replays
  cleanly.** Upstream's only meaningful EVM-layer change is
  `qtumledger.cpp` (+98/-43), which Runebase does not modify.
- **The Qt artwork is untouched upstream.** Of all Runebase asset files
  under `share/pixmaps` and `src/qt/res` (268 files), **zero** were
  changed by upstream between 29.1 and 30.2 — identical to the 29.1
  experience. Only **6** `src/qt` files conflict at all, and they are
  code/forms/locale, not assets.

## The three themes

### 1. Legacy (BDB) wallet removal — the dominant user risk

Bitcoin Core 30 removed legacy wallets; Qtum v30.2 inherits it. Verified
in the v30.2 tree:

- `src/wallet/bdb.cpp`, `bdb.h`, `salvage.cpp/h`, `depends/packages/bdb.mk`
  and its patch are **deleted**.
- `WITH_BDB` no longer exists as a CMake option.
- **BUT** `src/wallet/migrate.{cpp,h}` survive and `migratewallet` is still
  present (3 references in `wallet/rpc/wallet.cpp`). The read-only
  Berkeley parser is retained specifically so migration works —
  `walletdb.cpp` shows `BERKELEY_RO` can be opened only when
  `require_format` is set, "which only occurs in migration".

**Why this is acute for Runebase specifically:** during the v29.1.0
release we established that on a representative node, **only 1 of ~15
wallet files was SQLite** — everything else is BDB. We deliberately
shipped v29.1.0 with `WITH_BDB=ON` because a build without it refuses to
start when `settings.json` auto-loads a legacy wallet (this exact failure
cost us a debugging cycle; see CLAUDE.md). On v30.2 that workaround no
longer exists at any build setting.

Mandatory migration campaign, sequenced:

1. Ship guidance **now, on v29.1.0**, telling stakers and users to run
   `migratewallet` while a BDB-capable build is still the current release.
2. Verify migrated (descriptor) wallets stake correctly — already
   evidenced: `wallet/stake.cpp` branches on `WALLET_FLAG_DESCRIPTORS` and
   `runebase_pos.py --descriptors` passes.
3. v30.2 release notes must lead with this, not bury it.
4. Consider a startup check in the Runebase v30.2 build that detects a
   BDB file in the wallet directory and prints migration instructions
   rather than a bare "unsupported format" error. Small, Runebase-specific,
   high user value.

Also removed and worth an inventory pass against our tooling and docs:
`dumpprivkey`, `dumpwallet`, `importaddress`, `importmulti`,
`importprivkey`, `importpubkey`, `importwallet`, `addmultisigaddress`,
`sethdseed`, `newkeypool`, `upgradewallet`; and `getwalletinfo` drops
`balance`/`unconfirmed_balance`/`immature_balance` (use `getbalances`).

### 2. Qt 5 -> Qt 6 migration

83 `src/qt` files change upstream (excluding locale). Our exposure is
smaller than that number suggests because our Qt delta is mostly assets
and CSS:

- **Artwork/CSS: zero upstream conflicts** (measured above).
- **6 conflicting Qt files:** `bitcoingui.cpp` (carries the RRC-Tokens
  rebrand), `adddelegationpage.cpp`, `forms/overviewpage.ui`,
  `forms/signverifymessagedialog.ui`, and two locale files
  (`bitcoin_ko.ts`, `bitcoin_zh_CN.ts` — both carry the RRC rebrand).
- **New risk not visible in the diff:** Qt6 changes stylesheet and
  high-DPI behaviour. Runebase's `theme3` CSS and re-cut backgrounds were
  hand-tuned to fit the wallet; they must be **visually re-verified under
  Qt6**, not just merged. Budget real GUI testing time.
- Build environment: guix builds Qt itself, so `depends` handles the
  toolchain; a local dev build needs Qt6 dev packages alongside/instead of
  Qt5.

### 3. Structural refactors that touch our deltas

Files where Runebase carries a delta *and* upstream churned significantly:

| file | upstream churn | Runebase delta at risk |
|---|---|---|
| `src/validation.cpp` | +436/-478 | the 5 economic lines (premine, PoW reward, `halvings >= 1`, 100-COIN base, inflation guard) — and `CheckReward` if RIP-2 lands first |
| `src/init.cpp` | +227/-153 | `-rip1height` arg wiring |
| `src/wallet/spend.cpp` | +186/-144 | `OP_SENDER_SIGNATURE_SIZE` fee fix — **upstream hunks are in `AvailableCoins`/`FetchSelectedInputs`/`ListCoins`, not the fee-calculation block**, so a clean merge is likely but must be verified |
| `src/wallet/wallet.h` | +101/-108 | the 100x fee constants — upstream hunks are in wallet flags/private members, **no `FEE`/`FEERATE` lines changed** |
| `CMakeLists.txt` | +114/-95 | `-fwrapv` (RUNEBASE-only, upstream does not carry it) |
| `src/policy/fees.cpp` | +20/-6 | the fee-bucket auto-migration — **no upstream changes near the bucket-read path** |
| `src/kernel/chainparams.cpp` | +60/-37 | every network parameter, all fork heights, `nRIP1Height` |
| `src/consensus/params.h` | +10/-7 | `nRIP1Height` field (plus `nRIP2Height` if RIP-2 lands) |

`test/functional/wallet_dump.py` is the one file Runebase modified that
upstream **deleted** (the `dumpwallet` RPC is gone) — drop our HRP fix
with it, no action needed.

## Other upstream changes worth noting

- **Boost minimum raised to 1.82** (we build against 1.83 — fine).
- **AssumeUTXO** support: relevant to the CLAUDE.md "Known gaps" item that
  our regtest `m_assumeutxo_data` fixtures are still Qtum's. This upgrade
  is the natural time to regenerate them.
- `-natpmp` on by default replacing `-upnp`; `-proxy` gains per-network
  configuration; disk logging rate-limited to 1 MiB/hour.
- **`datacarriersize` default raised to 100,000** and multiple OP_RETURN
  outputs allowed. This is *policy*, but it interacts with Runebase's
  economics: our relay fee is 100x, so large OP_RETURN payloads cost 100x
  more here than on Qtum. Verify the interaction with
  `MAX_BLOCK_WEIGHT`/our block size DGP before adopting the default.
- TRUC (v3) transactions in the wallet; `bumpfee`/`psbtbumpfee` under
  full RBF; BIP324 v2 transport (off by default).
- Qt6 brings native dark mode on Windows and a Metal backend on macOS.

## Risk assessment

| risk | severity | mitigation |
|---|---|---|
| Users/stakers stranded by BDB removal | **high** | migration campaign starting on v29.1.0, before v30.2 ships |
| Qt6 breaks Runebase theming/backgrounds visually | medium | dedicated GUI verification pass; assets themselves are safe |
| Runebase delta silently lost in a 60-file merge | medium | the CLAUDE.md "hunt for LOSSES" token-count audit, plus `verify-runebase-values.sh` (now covering RIP-1 and release-build flags) |
| `validation.cpp` economic lines lost in heavy churn | **high impact / low likelihood** | the five-line rule in CLAUDE.md; diff against renamed upstream must show exactly those |
| RIP-1 gate lost | high impact / low likelihood | zero EVM-layer conflicts measured; verify script covers it |
| assumeutxo fixtures remain Qtum's | low | regenerate during this upgrade |

## Recommended plan

Reuse the proven 29.1 procedure (CLAUDE.md "Upgrade strategy"), which
this analysis has already exercised for measurement purposes:

| phase | work |
|---|---|
| 0 | **Do not start merging until the mainnet fork (block 2810000, ~2 Sep) is confirmed successful.** A v30.2 branch in flight must not distract from a live hardfork. |
| 1 | Validate the rename script against v29.1 (residual must be only known Runebase files) — the renamed trees for this analysis are already built |
| 2 | Three-way merge: base = renamed q29.1, ours = renamed q30.2, theirs = Runebase master. Use `git add -A -f` (the `.gitignore` `src/runebase` trap) |
| 3 | Replay the 60 conflicts, consensus/economics first; the 59 clean files should apply mechanically |
| 4 | Re-apply RIP-1 (should be clean), `-fwrapv`, fee constants, RRC rebrand; run `verify-runebase-values.sh` |
| 5 | Qt6 GUI verification pass — theming, backgrounds, high-DPI |
| 6 | Wallet migration tooling + release-notes campaign |
| 7 | Functional suite; regenerate assumeutxo fixtures; testnet sync |

**Estimated effort:** comparable to the 29.1 upgrade — the merge itself is
smaller and the EVM layer is free, but Qt6 verification and the wallet
migration campaign are new work that 29.1 did not have.

## Open decisions

1. **Timing** — v30.2 should not begin in earnest until the mainnet RIP-1
   fork is confirmed. Nothing in v30.2 is urgent; there is no new
   consensus feature to chase.
2. **Do we bundle RIP-2 (fee burning) with the v30.2 fork?** Arguments
   both ways: bundling avoids a second mandatory upgrade for users, but
   it re-introduces consensus risk into what is otherwise a
   non-consensus release, and RIP-2 would permanently add a delta to
   `CheckReward` in a file already seeing +436/-478 of upstream churn.
   **Recommendation: keep them separate.** Ship v30.2 as a pure
   maintenance/wallet upgrade; schedule RIP-2 as its own fork afterwards.
3. **Qt6 minimum version** and whether to adopt upstream's raised
   `datacarriersize` default given our 100x fee scale.
